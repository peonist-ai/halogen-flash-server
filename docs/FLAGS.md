# halogen environment flags

Everything is configured by environment variable; there is no config file.
All flags are read **once at startup**.

This lists the flags used to deploy and operate halogen. The engine carries
additional kernel-tuning levers that are not documented here: they select
internal implementation variants, they are not needed to run the server, and
the shipped defaults are the measured winners. Changing what is listed below
is supported; anything else is not.

| class | meaning |
|---|---|
| **BITWISE** | output is byte-identical. Safe to change. |
| **NUMERIC** | output *can* change. |

Every flag below is **BITWISE**, deployment policy rather than arithmetic, except
`HALOGEN_CK_OVERLAY`, which selects which weights run,
`HALOGEN_MATMUL_TUNING_FILE`, which changes the order a sum is accumulated in,
`HALOGEN_INDEXER_BUDGET`, which changes how much of the context the model
attends, and `HALOGEN_COMPOSABLE_CONTEXT`, whose reused answers are close to
but not byte-identical to fresh ones. Each is marked, and each was measured
before being offered.


## Model and tokenizer

| flag | default | meaning |
|---|---|---|
| `HALOGEN_CHECKPOINT` | `/models/qwen38-flash-next-w4b.hgn` | Path to the `.hgn` checkpoint the engine loads. **The served checkpoint is two files**: this one and the quality sidecar `<checkpoint>.overlay.hgn` beside it, which the engine picks up on its own. The server says at startup which precision it is about to run, and warns if the sidecar is absent. **Since 0.7.0 it may name a llama.cpp GGUF of the model instead** (any shard of a split; the siblings are found by name): the engine repacks it into RAM at startup, losslessly, reads its lookup table in place and takes the draft head from `HALOGEN_MTP_HEAD`. The README's *Bring your own GGUF* has which files are read and what it costs; since 0.12.1 the image's `convert` mode writes that repack out as a complete `.hgn` this variable can name instead (no GGUF beside it, no sidecar looked for). |
| `HALOGEN_DOWNLOAD` | *(unset = off)* | A Hugging Face repo id to fetch the weights from on first start (`peonist-ai/halogen-qwen3.8-flash-next`). Off by default, which is what keeps the container free of all outbound connections. Fires only when the checkpoint is missing (a start with it set and the volume writable also refreshes the 2.4 GiB quality sidecar when the one on disk predates the image; the 115 GiB checkpoint is never re-fetched); partial transfers resume. Needs the models volume mounted read-write. The checkpoint's presence is verified after the download rather than trusted, so a truncated tree fails here rather than later and more confusingly in the engine. **BITWISE**: it moves bytes onto disk, it does not change arithmetic. |
| `HALOGEN_MTP_HEAD` | `qwen38-flash-next-mtp.hgn` beside the checkpoint | The engine's draft head for a GGUF trunk (1.4 GiB, on the weights repo; fetched by `HALOGEN_DOWNLOAD` when the volume is writable). A GGUF carries no draft head this engine can run, so without this file a GGUF does not start, and the entrypoint says so before anything is loaded. Not read for the engine's own checkpoint, which carries its head. |
| `HALOGEN_GGUF_CACHE` | *(unset)* | `1` writes the repacked weights out once beside the GGUF as a file the engine can load directly on later starts (about 70 GiB for an 8-bit trunk; `=<dir>` puts it elsewhere; the volume must be writable and have the room, or the write is skipped with a line and the server starts anyway). It is checked against the shards' sizes and modification times on every start and is never used stale: rebuilt with this set, ignored without, both said in the log. Measured on the reference machine: a restart is 1.4 s from a warm file and 16 s from a cold one, against the repack's 9 s warm and 18 s cold, so it buys seconds, not minutes; it is for a host that restarts often from a warm cache. |
| `HALOGEN_GGUF_THREADS` | `8` | Workers for the repack of a GGUF at startup. The output does not depend on the count. 8 and 16 read the reference machine's NVMe drive at the same rate, so more only helps a host whose CPU is slower than its drive. |
| `HALOGEN_CK_OVERLAY` | *(unset = the sidecar)* | Which precision sidecar to read. Unset means the quality sidecar beside the checkpoint, **which is the default and needs no action**. Point it at `…overlay-speed.hgn` to trade the `o_proj` calibration for about 2% of decode, or `none` to run the bare 4-bit checkpoint, which is the measurement control rather than a serving configuration. **NUMERIC**: it selects which weights run. |
| `HALOGEN_TOKENIZER` | `/tokenizer` | Flat tokenizer directory. **You usually do not need to set this**: the weights repo ships `tokenizer/` inside it, and when nothing is mounted at `/tokenizer` the server falls back to `tokenizer/` beside the checkpoint, so one `-v` of the models directory is enough. Set it only when your tokenizer lives elsewhere. It must be FLAT: HuggingFace cache snapshots are symlinks into a sibling `blobs/` and dangle inside a container, so materialize with `cp -L`. |
| `HALOGEN_MODEL_ID` | `halogen-qwen3.8-flash-next` | The model id listed at `/v1/models`, reported at `/health`, and echoed in every completion. A label. Requests are never rejected for naming a different one. Override it to run two stacks on one host without the ids colliding. |
| `HALOGEN_TEMPLATE_UNCHECKED` | *(unset)*: the chat template is probed and a failure refuses to start | Whether to serve a chat template whose thinking control does not work (0.12.2). At startup the server renders a one-message conversation with `enable_thinking` false and true and requires the first to carry the empty think block and the second not to close it; every thinking control (`enable_thinking`, `reasoning_effort: "none"`, `HALOGEN_ENABLE_THINKING=0`, the budgets) depends on that branch, and a template from another repository without it would accept them all and render thinking anyway. The weights repo's own `tokenizer/` passes. On a failure one sentence names the file and the container does not start; `1` prints the same sentence and serves it. The startup line and `/health.chat_template` name the template (path, sha256 of its text) and the probe's result either way. It changes no request. |

## Networking

| flag | default | meaning |
|---|---|---|
| `HALOGEN_API_PORT` | `8731` | Port for the OpenAI-compatible front-end. The only port that should be published. |
| `HALOGEN_PORT` | `8730` | Engine port. **The engine protocol has no authentication**, so keep it unpublished. |
| `HALOGEN_BIND` | `127.0.0.1` | Engine bind address. Loopback when engine and front-end share a container; `0.0.0.0` for the two-container topology, where it stays unpublished to the host. |
| `HALOGEN_ENGINE` | `127.0.0.1:$HALOGEN_PORT` | Where the front-end reaches the engine. Compose gives the services separate network namespaces, so it needs `engine:8730` there. |

## Request policy

| flag | default | meaning |
|---|---|---|
| `HALOGEN_MAX_TOKENS_CAP` | `65536` | Largest `max_tokens` a request may ask for. Exceeding it is a **400**, never a silent truncation: a truncated response and a model that stopped on its own both end with `finish_reason: "length"`, so a client cannot tell them apart. **Coupled to `HALOGEN_QUEUE_TIMEOUT`**, see the README. |
| `HALOGEN_KEEPALIVE_TIMEOUT` | `300` | Seconds an idle keep-alive connection is held open before the server closes it. Agent clients idle between turns for as long as a tool call or a person reading takes, and a `POST` on a socket the server has just closed is not retried transparently by most HTTP clients, so a short value turns a rare race into a constant one. Releases before 0.5.7 never set this and got the framework default of 5 seconds. An idle connection costs a file descriptor and holds no conversation slot, so raising it is cheap; lower it only if you are fronting many short-lived clients. |
| `HALOGEN_SSE_KEEPALIVE_S` | `10` | On a streaming response, an SSE comment line (`: keepalive`) is sent whenever nothing else has been for this many seconds: during a long prefill before the first token, and anywhere else the model is quiet. SSE parsers ignore comment lines, and every HTTP client's inactivity timer resets on one. Node's undici (Pi, Qwen Code) closes a body that is silent for 300 s with no client-side setting, which is what a long tool call looked like before 0.6.1. `0` disables it. |
| `HALOGEN_QUEUE_TIMEOUT` | `3600` | Seconds a queued request waits before `503 engine_busy`. Must exceed the time a full-length request takes, or a long request 503s everyone behind it. |
| `HALOGEN_MAX_TOKENS_DEFAULT` | *(unset: 8192 on chat and responses, 128 on completions)* | The token budget a request gets when it sends none. One variable moves every route's default. Must not exceed `HALOGEN_MAX_TOKENS_CAP` or the server refuses to start. A request that sends a budget always wins. Reported by `/health` as `max_tokens_default`. The budget bounds reasoning AND content, so a small default removes the answer rather than shortening it. |
| `HALOGEN_TEMPERATURE` | *(unset: greedy)* | The sampling temperature for a request that sends none, 0 to 2. Qwen's recommended settings for this model are sampled (`generation_config.json`: temperature 1.0, top_p 0.95, top_k 20; the card's instruct point is 0.7 / 0.8 / 20 with presence_penalty 1.5), and most agent clients send no sampling fields, so this is how you run those settings without every client cooperating. **The rule, for this and the five below:** a field the request sends always wins; a default fills only a field the request omits; a request that sends `temperature: 0` decodes greedy and takes none of the sampling defaults. Setting this moves every request that sends no temperature off the greedy path, which is the only path the byte-identical guarantees are made on. `/health` reports what is set under `server_defaults` and says which path a temperature-less request takes. An out-of-range value refuses to start, before the model loads, naming the variable. |
| `HALOGEN_TOP_P` | *(unset: no nucleus filter)* | `top_p` for a request that sends none, 0 to 1. Applies only when the request samples (its own temperature or the server's). A request that sends `top_p` wins. |
| `HALOGEN_TOP_K` | *(unset: no top-k filter)* | `top_k` for a request that sends none; 0 disables. A request that sends `top_k`, including 0, wins. |
| `HALOGEN_MIN_P` | *(unset: off)* | `min_p` for a request that sends none, 0 to 1. Same rule. |
| `HALOGEN_PRESENCE_PENALTY` | *(unset: 0)* | `presence_penalty` for a request that sends none, -2 to 2. Penalties are sampler-only, so it applies only when the request samples; on a greedy request it is simply not applied. A request that sends a penalty without sampling is still a 400, and a request that sends `presence_penalty: 0` disables the default. |
| `HALOGEN_FREQUENCY_PENALTY` | *(unset: 0)* | `frequency_penalty` for a request that sends none, -2 to 2. Exactly as `HALOGEN_PRESENCE_PENALTY`. |
| `HALOGEN_REASONING_EFFORT` | *(unset: the chat template's own `xhigh`)* | The reasoning effort for a request that names none: `minimal`, `low`, `medium`, `high` or `xhigh` (the template has three levels: `minimal` maps to `low`, `medium` maps to `medium`, `high` maps to `xhigh`). This is the largest budget lever there is: `xhigh` thinks for hundreds to thousands of tokens on an agentic prompt, and that spend comes out of `max_tokens`. A request that sends `reasoning_effort`, `chat_template_kwargs.reasoning_effort`, or `reasoning.effort` on `/v1/responses` wins. Reported by `/health` as `reasoning_effort_default`. |
| `HALOGEN_ENABLE_THINKING` | *(unset: the chat template's own default, thinking on)* | Whether a request that does not say renders the thinking block. `0` renders what `enable_thinking: false` renders (no reasoning, the model answers directly, the model card's instruct settings then apply); `1` is the template's default made explicit. A request that sends `enable_thinking` (top level or in `chat_template_kwargs`) wins. `/v1/responses` has no such field, so this is the only way to run that route without thinking. Reported by `/health` under `server_defaults`. Any other value refuses to start. |
| `HALOGEN_MAX_THINKING_TOKENS` | *(unset: no budget)* | The thinking budget for a request that sends none (0.8.1, issue #56): at most this many generated tokens inside the think block; if the model has not closed it by then the server does (the model's own budget sentence, then `</think>`) and the answer follows in the same stream. A request's `max_thinking_tokens` (or any of its aliases: `thinking_budget_tokens`, `thinking_budget`, `thinking_token_budget`, `reasoning.max_tokens`, `thinking.budget_tokens`) wins. `max_tokens` still covers thinking and the answer together. |
| `HALOGEN_THINKING_ANSWER_ROOM` | *(unset: `max(1024, 15% of the request's max_tokens)`)*; `0` = off | The answer room (0.11.0). When a request sends no thinking budget, the think block is closed with this many tokens of `max_tokens` left for the answer (the same close as `max_thinking_tokens`: the model's budget sentence, `</think>`, then the answer), so a capped request ends with content instead of `finish_reason: length` and an empty `content`. Agent harnesses send no thinking control to a custom server unless configured to, so the model's `xhigh` ran under whatever cap the harness set for the answer; a compaction capped at 13,000 tokens that the model thought past was a failed compaction. A request's own budget wins when it is smaller. Only a request whose thinking would have run past the line is affected. `/health` reports `thinking_answer_room`. |
| `HALOGEN_DRAFTER_DEFAULT` | `1` | Which drafter a request that names none gets: `1` the model's own MTP head (speculative, and **byte-identical** to serial greedy, since it only proposes), `0` batched serial. A speculating request speculates while it is the only one generating and joins the batch as soon as another request is active, so the setting costs no concurrency. Overridable per request with `"drafter": "serial" | "mtp"`. |
| `HALOGEN_PLD` | `3,3` | Prompt lookup beside the MTP head, as `N,K`: when the last `N` tokens the request has produced also occur earlier in its own context (the prompt or what it has generated), the `K` tokens that followed that earlier occurrence are proposed as one chain and verified in a single step, and the head's own draft must open the chain. It drafts from the request's text, never from a model, so it pays where an answer repeats its context: tool-call arguments, file paths, code that quotes the file being edited. **Byte-identical** to serial greedy, like the head: every committed token is the model's own choice. Applies to greedy requests only, and, like the head, while the request is the only one generating; a sampled request uses the head alone. `0` turns it off. `K` above 3 needs more verify rows than the image reserves and the server says so at startup. |
| `HALOGEN_SPEC_ADAPT` | `32,0.35,64` | The MTP head's adaptive policy, as `W,floor,R`: acceptance is read over windows of `W` drafting rounds; when a window falls under `floor` the head is switched off for the next `R` tokens (the request decodes serially, which is faster than drafting that keeps being rejected, as on some prose), then a window is tried again. `0` never adapts (the head drafts every round). **Byte-identical** to serial greedy either way: the head only proposes, so every committed token is the model's own choice; the policy moves speed only. A sampled request runs the same policy with the acceptance coin in place of the argmax match. |
| `HALOGEN_GRAMMAR` | `1` | Structured output: whether a `response_format` of `json_schema` / `json_object` (`text.format` on `/v1/responses`) is enforced while decoding. `1`: the schema is compiled once per distinct schema (a millisecond), every state's token mask lives on the GPU (up to 31 MB a schema, eight schemas cached), and each token is the greedy choice among the tokens the schema allows next, so the reply parses and validates by construction; a request without a schema is byte-identical to what it was, and a constrained request is identical serial, with the head, with prompt lookup and beside other requests. The README lists which schema keywords are enforced, which are accepted without being enforced, and which are refused by name; `/health` lists the same under `structured_output`. Greedy only: a sampled request with a schema is a 400, and so is a schema with an image. `0`: every schema is a 400, as before 0.8.0. |

## Images

| flag | default | meaning |
|---|---|---|
| `HALOGEN_VISION_TOWER` | *(unset: images are refused)* | Path to the vision sidecar, or `1` to look for it beside the checkpoint. Unset, the server takes text only and an image is a **400** naming this flag, which is the shipped default: with no tower the image path is not merely disabled but absent, so text behaviour is byte-identical to a build without it. Set, `/health` reports `vision.enabled` and both `/v1/chat/completions` and `/v1/responses` accept an image content part as a `data:` URL or bare base64. Fetching an `http(s)` URL is refused by design, since that would make the server issue outbound requests on a client's say-so. |
| `HALOGEN_VISION_MAX_PIXELS` | `3686400` (2560x1440) | The most pixels an image is given before it is downscaled to fit, preserving aspect ratio. **Nothing is refused for being large** until four times this, which is a guard on decode cost rather than a quality limit. Measured end to end, one image costs about 5.5 / 11.8 / 25.3 / 105.8 seconds at 1280x800 / 1920x1080 / 2560x1440 / 3840x2160, and 4K reads no better than 1440p, which is why the default sits there. Images below 256x256 are scaled UP, which helps rather than hurts: a downscaled frame reads small text at least as well as a native one at the same final glyph size. Text at 12 pt and above is read exactly at every supported resolution; below that it degrades gradually rather than failing, and a densely filled page is harder than a sparse one at the same point size. |

## Context and concurrency

| flag | default | meaning |
|---|---|---|
| `HALOGEN_KV_SLOTS` | `4` | Conversations generating at once. A slot costs about 115 MB; the pool below decides what fits. Each stream is **byte-identical to running alone**. Four streams together produce about 76 tokens per second in total, each at 11 to 19; eight produce about 85, each at about 10, so raising it trades per-stream speed for admitting more clients at once rather than queueing them. Past eight a step takes two forwards and total throughput stops growing. Capped at 64. |
| `HALOGEN_KV_POOL_POSITIONS` | `2 x HALOGEN_CTX`, capped at 1,048,576 | Attention positions resident across all conversations; `HALOGEN_CTX` is the most one request may use. A request reserves its prompt plus `max_tokens` positions when admitted and waits in arrival order when they are not free. The default 524,288 holds two full-length conversations, about 35 GB on the device; 786,432 holds three at about 42 GB (0.3.0 defaulted to it and it is too close to the ceiling on some machines) and 1,048,576 needs `HALOGEN_MAX_TOK=16384` (about 41 GB). The server measures the device budget at startup and lowers the pool itself if the configured one will not fit, saying what it chose. Generation speed follows each conversation's own length, not the pool. The pool takes RAM the page cache would otherwise keep for the model's n-gram table, so a prompt whose rows are not cached reads them from disk first; a smaller pool leaves more cache. |
| `HALOGEN_KV_POOL_FIT` | `1` | Whether the server measures the device budget at startup and lowers `HALOGEN_KV_POOL_POSITIONS` when the configured pool will not fit, printing the pool it settled on. `0` allocates exactly what was asked for and lets the allocation fail, which is what every release before 0.3.1 did. It can only lower the pool, never raise it, and it never lowers it below `HALOGEN_CTX`; a shorter pool changes how many conversations stay resident and changes nothing about what any one of them computes. |
| `HALOGEN_HOST_RESERVE_GIB` | `20` | How much system RAM the server leaves free, on top of the weights, when it sizes the KV pool at startup. The model keeps a large lookup table on disk and reads it through the file cache rather than holding it in memory, so RAM the pool takes is RAM that table loses. Too little and the server starts, runs, and then crawls on long prompts with the disk busy. Raise it if you see that; a smaller pool is the trade. |
| `HALOGEN_CTX` | `262144` | The most context ONE request may use, **the model's full native context, by default**. A prompt over the limit is a hard error naming it, never a truncation. The published quality numbers cover 1k-32k; beyond that the context is served but unscored. |
| `HALOGEN_ADMIT_CHUNK` | `0` (the engine's own prefill chunk) | How a prompt is read in when other conversations are already generating: in pieces, with a generation step for the others between pieces. The default piece is the prefill call size (`HALOGEN_MAX_TOK`, 32,768), which is exactly how the same prompt is split when it runs alone, so the answer stays byte-identical to running alone; a 131k prompt pauses the others three times for about 28 s each instead of once for 105 s. `HALOGEN_MAX_TOK=16384` halves the pause for everyone at about 8% slower prefill and keeps identity. A smaller value such as `8192` (measured: a 32k prompt pauses the others about 8 s rather than 28, and pays about 5 s on its own first token) trades that identity for the admitted prompt, whose answer then depends on the load when it arrived. `-1` reads every prompt in one call. |
| `HALOGEN_CACHE_ENTRIES` | `24` | How many prompt-cache entries the server keeps, least recently used out. A conversation holds five: one at the end of its system prompt, its three most recently used history entries (0.11.0, issue #61: a harness that sends the history plus a side question and then drops that turn continues from where the side turn branched, and with one history entry that point was gone; a third since the start of the last user message became a saved place, see `HALOGEN_CACHE_SNAP3`), and since 0.11.3 one at the end of its last request, which serves an exact repeat of that request without reading anything again. Twenty entries cover four conversations, and requests that share a system prompt and ask different things resume from it. Each entry is about 115 MB of RAM plus the pool positions its content covers, which stay reserved while it exists. When the pool is full the server forgets the least recently used conversation's region, never the entry the request is about to resume from, and prints a `kv pool: no room ...` line for each one. |
| `HALOGEN_CACHE_BRANCHES` | `2` | How many branches of one conversation the prompt cache keeps resume points for. Two is a conversation plus one side turn. **Three is a parent forked into two children**, which is what a harness fanning out subagents runs: on two, the parent's resume point is the one the children's stores replace, so the parent re-reads its history on its next turn. Raising it costs host memory in whole entries (about 115 MiB each) and raises the `HALOGEN_CACHE_ENTRIES` default with it, since that default is derived from this: `3` gives 32 entries and about 3.5 GiB against `2`'s 24 and 2.7. It changes only what is cached, never what an answer is. |
| `HALOGEN_CACHE_SNAP3` | `1`; `0` = off | Whether the prompt cache also saves its place at the START of the last user message. A client that keeps a document in one message and asks each new question in the next (`[doc][question 1]`, then `[doc][question 2]`) matched neither of the other two places (the end of the previous question, the end of the system prompt), so every new question re-read the document and only an exact repeat was served from the cache; with this on the second question resumes from the end of the document. Costs nothing measurable on the first request (since 0.12.1 the state is recorded as the pass goes by; the fixed cost of a save is about 0.1 s) and nothing on a hit. Harnesses that extend their history every turn were served by the other places already and are not changed by this. A one-message request (with or without a system prompt) has nothing behind its question and gets no third place. |
| `HALOGEN_CACHE_FULL` | `1`; `0` = off | Whether the server keeps the end-of-request entry (0.11.3): the state at the end of every prompt plus its last logits, one per conversation, so an exact repeat of a request answers byte for byte its first answer and reads nothing again. `0` returns to three entries per conversation and about 115 MB less RAM per conversation; a repeated request then resumes from the nearest history entry, as before 0.11.3. |
| `HALOGEN_MAX_TOK` | `32768` | Largest single prefill call; longer prompts are prefilled in pieces. It sizes a ~4 GB scratch arena, so **do not raise it to the native context**. That allocation does not fit and the server will not start. |
| `HALOGEN_CACHE_INPLACE` | `1` | The prompt cache keeps the conversation's attention state where it already is and saves only the small position-free state (about 110 MB at any context), so saving and resuming cost well under a second even at 1M. `0` copies the whole state instead (up to 26.6 GB at 1M); it is the older form, kept for comparison, and gives the same answers byte for byte. |
| `HALOGEN_CACHE_FILE` | *(unset)* | Keep the prompt cache's snapshot in a file at this path instead of host RAM: the same bytes, at the drive's speed. Only needed with `HALOGEN_CACHE_INPLACE=0` past 262,144, where that form's snapshot is up to 26.6 GB; the container then sets it to `/var/tmp/halogen-cache.snapshot`. The file is created at startup and removed at exit. |
| `HALOGEN_ROPE_YARN` | *(unset)* | Contexts past the native 262,144, up to 1,048,576. Set it to the model card's static YaRN factor (`4` for 1M, `2` for 524,288) together with a larger `HALOGEN_CTX`; the server refuses a context past 262,144 without it, and past 262,144 x factor with it. It is a different model configuration, not a cache setting: every position's RoPE is rescaled, short prompts included, and the model card advises it only when the context needs it. Past the native context the server caps `HALOGEN_MAX_TOK` at 16384 and prints it, because a 1M KV cache leaves no room for the larger prefill arena on a 128 GB machine. The README's *1M context* section has what it costs. Unset, nothing changes. |
| `HALOGEN_INDEXER_BUDGET` | *(unset)* = 2048 | The model's sparse-attention budget: how many tokens of the context each query attends (the top `budget / 4` blocks by the model's own indexer, plus the tail). The checkpoint's value is 2048 and is the default. Any value from 2048 to 8192, rounded down to a multiple of 16, is accepted; the effective value is printed at startup and reported by `/health` as `indexer_budget`. Set higher, it is a different model configuration, not a cache setting: every query past the budget attends a superset of what the checkpoint was trained on, so long-prompt answers are not byte-identical. Static for the server's life. The README's *Attention budget* section has what 4096 and 8192 bought and cost when measured: two more of 96 planted facts retrieved at 16k for about 7% of prefill speed at 32k and 2% of decode at 4096; every fact at 8192, at a consistent perplexity cost and a fifth of prefill. Unset, or set to 2048, nothing changes. |

## Speed levers

| flag | default | meaning |
|---|---|---|
| `HALOGEN_PROMPT_CACHE` | `2` (resume anywhere) | Reuse a session's shared prefix instead of re-reading it. **`2` (default)** saves its place at the end of every request, so a follow-up turn at 100,000 tokens of context costs about 2 s against 88 s cold, at any prompt length. **`1`** saves only on a prefill-chunk boundary, which makes a resumed answer byte-identical to a cold one, at the price of caching nothing below one chunk. **`0`** is off. The README's *Choosing a cache mode* has the numbers and the cases. **NUMERIC** in mode 2. |
| `HALOGEN_PREFILL_CHUNK` | `32768` | How many tokens the engine prefills per call. Under the default cache mode this is purely a speed setting and 32,768 is the fastest value measured; 1,024 costs about half the throughput at long context. Under `HALOGEN_PROMPT_CACHE=1` it is also the resume granularity, so lower it to 8,192 if you need byte-identical repeat answers on conversations shorter than 32,768 tokens, at about 13% less prefill throughput. |
| `HALOGEN_CACHE_DIR` | *(unset)* = the prompt cache lives in memory only | Persist the prompt cache to this directory so a conversation survives a server restart (0.10.0; issue #40). Each turn's new state is written behind the request, nothing on the request path waits, and a conversation no longer in memory is restored from disk on its next turn; the restore is byte-identical to the in-memory resume. About 27 KiB per token. Every build, weights file and setting keeps its own files and never restores another's. Needs a filesystem that accepts direct I/O (a tmpfs or overlay is refused and the cache stays in memory). See the README's *Prompt cache on disk* section. |
| `HALOGEN_CACHE_DISK_GIB` | `64`; `0` = unbounded | The directory's size bound for `HALOGEN_CACHE_DIR`: least recently used conversations are removed when a new one would pass it. |
| `HALOGEN_CACHE_PRUNE_OLD` | `0` (keep) | `1` removes, at startup, the other builds' and configurations' subtrees under `HALOGEN_CACHE_DIR` (0.11.10; issue #78). Each engine build, weights file, context size or numeric setting keeps its own subtree there and `HALOGEN_CACHE_DISK_GIB` bounds only the current one, so an upgrade leaves the old build's files behind until something removes them. The default keeps them (a rollback finds its cache warm); with `1` the startup log names each subtree removed and its size. Only directories the cache itself wrote are candidates; anything else in the directory is left alone. |
| `HALOGEN_COMPOSABLE_CONTEXT` | `0` (off) | **NUMERIC, opt-in preview.** `1` retains each message at or above `HALOGEN_COMPOSABLE_CONTEXT_FLOOR` as it is first read and reuses that work when a later request repeats the message at any position behind the same system prompt: the shape of an agent harness's compaction. A reused answer is very close to, not byte-identical to, the answer from reading the text fresh. Needs `HALOGEN_PROMPT_CACHE=2` and `HALOGEN_KV_POOL=1` (the defaults); image requests are not composed. `/health` reports it under `composable_context`. See the README's *Composable context* section. |
| `HALOGEN_COMPOSABLE_CONTEXT_FLOOR` | `2048` (tokens) | The smallest message composable context retains and reuses. Messages below it are read fresh every time. |
| `HALOGEN_COMPOSABLE_CONTEXT_BYTES` | `4294967296` (4 GiB) | The host-memory budget of the retained messages, least recently used out; each retained message costs about 230 MB whatever its length, so the default holds about 18. In the server's memory, not on disk, and gone at restart. |
| `HALOGEN_MATMUL_TUNING_FILE` | `/opt/halogen/flash-tune.plan` (baked in) | A tuned GEMM plan: which kernel the matrix library should use for each shape, decided once and shipped in the image. On by default at no measurable quality cost, and the published prefill numbers include it. Every process reads the same decisions, so the same prompt keeps giving the same answer. The plan is tuned on one machine; a different Strix Halo SKU loads it with a warning. To retune for your own workload, point this at a path that does not exist yet, run with `HALOGEN_MATMUL_ALGOS=8`, and stop the container cleanly. **Do not set `HALOGEN_MATMUL_ALGOS=8` without a file**: selection then happens per process by timing, and identical prompts stop answering identically across restarts. |
| `HALOGEN_NGRAM_GATHER_THREADS` | `64` | How many rows of the model's lookup table are read at once when a prompt needs rows that are not in the file cache. The table (47.7 GiB) is read through the page cache and never held in RAM, and on a 128 GB machine running this server there is never room to cache all of it, so the first long prompt after a restart, or any long prompt on a host with little RAM to spare, reads its rows from disk: one 4 KB random read per row. Before 0.6.3 those reads were issued one at a time; a 32,768-token prompt paid 46 to 52 s on top of its usual 25 s with the table evicted, 13.5 s on an 8,192-token one. At 64 in flight the same prompts pay about 1.3 s and under half a second on an NVMe drive (8 threads 7.3 s, 16 and 32 about 3 s, 128 no better than 64). Same bytes, same output. `1` restores the old loop. The log line `lookup table: ... took N s on N threads` reports any read of 2 s or more, and the health check keeps being answered through it. Decode reads 16 rows a token and is unchanged. |

## Troubleshooting

| flag | default | meaning |
|---|---|---|
| `HALOGEN_VERBOSE` | `0` in this image | Whether the server narrates how it is armed at startup, on top of what it is serving. Off in the published image, where the extra lines are internal detail rather than anything a deployer acts on. Set it to `1` when you are diagnosing a start that goes wrong and want the fullest account the server can give. |
| `HALOGEN_STARTUP_PROGRESS` | `1` (on) | Whether the server says which startup step it is on and how long it has taken: pinning weights, preparing them layer by layer, reserving working memory, reserving the KV pool, ready. A first start reads about 68 GB off disk, so on a slow or busy machine the wait is minutes, and these lines are what tell you it is progressing rather than stuck. Leave it on. If you report a slow start, the log with these lines in it is the single most useful thing to attach. |
| `HALOGEN_ENGINE_WATCHDOG_S` | `180` (seconds); `0` = off | How long the engine may go without answering the container's liveness probe before the container is taken down so a restart policy can recover it. It is for an engine that is alive and answering nothing, which nothing else can see: the process is up, the port accepts, the health check stays green. Silence inside the kernel does not count: before a silent probe counts, the container reads the engine's thread states and the kernel's memory-compaction counter, and an engine in uninterruptible sleep or a kernel compacting memory for it is a host short of memory, not a wedge. That silence is logged (`not counted as a wedge`) and the clock restarts when it ends. Killing an engine in that state is what left the driver holding its GPU memory after the process was gone on the host in #79, the end state three other hosts reached by other unclean exits (#34), after which every later start hangs until the host reboots. On a host that shares its memory with other work, raise it or turn it off before relying on a restart policy. |
| `HALOGEN_ENGINE_WATCHDOG_DEFER_S` | `900` (seconds); `0` = no cap | How long the watchdog keeps deferring a silent engine because the kernel's memory-compaction counter is climbing, before it counts the silence as a wedge and takes the container down anyway. The counter is host-wide, so on a machine that compacts memory without pause it says nothing about this engine, and before 0.12.3 the deferral had no end: one host sat with a wedged engine at 100% of a core and the container up for 30 minutes (issue #85). Past the cap, an engine whose threads are running and not inside the kernel is taken down with a line that says why. An engine with a thread in uninterruptible sleep is still never killed: the signal would not reach it, and that kill is what leaves the driver holding GPU memory (issue #79). Raise it if your host compacts memory constantly and your stalls really do clear in more than fifteen minutes; `0` restores the unbounded deferral. |
| `HALOGEN_ENGINE_WAIT_S` | `0` (wait as long as the load takes) | How long the container waits for the engine to finish loading before giving up. The default waits indefinitely and watches the engine process, so a machine that needs twenty minutes to load gets twenty minutes, and a crash is still reported immediately. Set a number of seconds if you would rather the container fail than wait, for example under an orchestrator with its own startup probe; on expiry the container exits with a message saying the engine was still loading. |
| `HALOGEN_FLASH_PIN_TRUNK` | `1` (on) | Whether the weights are locked into memory. On, they are, and that is what the published decode speeds are measured with. **This is the setting to reach for if you run other large workloads on the same machine.** Loaded, this server holds most of the host, and what is left is mostly not in the large contiguous pieces a big allocation needs. If your other processes then take the remainder, both they and this server can stall for minutes at a time at full CPU with no disk activity and no output. That is not a crash and needs no restart. Setting `0` gives a great deal of memory back and costs **several times the decode speed** (6 tokens/s against 37 on the reference machine; every prompt of 64 tokens or more first copies each layer's experts onto the GPU, about 7 s at any length when the weights are in the file cache and 25 to 50 s when the kernel has let them go to disk, so a 32k prompt reads within a few percent of pinned at best and a short one several times slower), so it is a last resort rather than a tuning option; a machine of its own is the better answer. Through 0.12.1 the setting did not work at the shipped settings (the first request ended the server with `internal sizing error in the per-forward arena`, issue #83); since 0.12.2 it does. The startup line reports how much room is left. |
| `HALOGEN_FRAG_WARN_BLOCKS` | `512` | When to warn that the host's free memory is in the wrong SHAPE. Free memory can be plentiful and still have almost none of it in large contiguous pieces, which is the normal state for a few minutes after a large process exits. Every big allocation then stops to compact memory, most of those attempts fail, and startup can take tens of minutes at 100% of one core with no disk activity and no output, which looks exactly like a hang. Before allocating anything the server counts the free 2 MiB contiguous blocks and warns below this many. An idle machine has thousands. If the warning appears, stop other large workloads and, as root, `echo 1 > /proc/sys/vm/compact_memory` before starting again. Raise the number to see the warning on a healthy host; `0` turns it off. |
| `HALOGEN_FRAG_WARN_STALLS` | `1000` | The same problem measured directly instead of predicted: how many times a startup step had to stop and compact memory before it could get the pages it asked for. The server reports the count for each step and warns above this many. A healthy machine does almost none. Set `0` to make it report on every step, which is how to see what the line looks like; a negative number turns it off. |
| `HALOGEN_DMALLOC_LOG` | `0` | `1` prints every device allocation of 64 MB or more as it happens, with its size, a running total and a count. It is this configuration's memory budget measured rather than estimated, and it is the right thing to attach to a report about a server that will not start. **A number of 2 or more is a size in bytes instead**, so a small value such as `4096` reports every allocation however small: that is the setting for asking what happens while requests are being served, as opposed to during startup. It prints sizes and totals only. |
